## 0. 一页纸结论

| 你的问题 | 结论（一句话） |
|---|---|
| 特色怎么立住 | 不做「语音版 ERP」，做「**一句话记一笔账**」：语音只负责降低输入门槛，账目安全靠「结构化回显 + 人确认 + 影响预览 + 反做单」四重兜底 |
| 端怎么分 | **一个小程序，两种屏幕**：手机 = 主录入端（语音大按钮）；**电脑版微信里跑同一个小程序** = 重度查看与管理。**不做网页版、不做账号密码、不记网址**；没有电脑也能用 |
| 上线形态 | **微信云托管 + D 方案** → 免自有域名、免 ICP 域名备案、免 HTTPS 证书、免配服务器域名；但**「小程序备案」（AppID 备案）必做**，与域名无关，T01 并行启动 |
| 怎么收款 | 软件订阅属虚拟商品 → **必须走小程序虚拟支付** `wx.requestVirtualPayment`，不得用普通商户号、不得引导外部付款；**发货回调走云开发云函数消息推送（已核实），不把域名带回来** |
| 怎么定价 | **一次性购买 30 天权益 + 语音加油包**（道具直购），**不做自动续费订阅**；免费 ¥0 / 基础 ¥9~19 / 专业 ¥29~49 / 门店版 ¥79~199 起（均需核实）；**失败不扣次**、超额**降级不断服**；渠道抽成计入毛利 |
| 命令要全面 | **12 个业务域 / 38 个 intent / 18 个槽位 / 4 档风险 R0~R3 / 4 档确认 C0~C3**，另有 12 类歧义冲突清单与 10 项高风险白名单 |
| AI 成本怎么控 | **不只是「限时长 + 排非命令」，而是六层漏斗**：端侧门禁 → 非命令过滤 → **规则/模板层优先（不调 AI）** → LLM 兜底 → 澄清状态机 → 确认卡片。AI 只干歧义消解、多商品拆分、模糊指代 |
| 确认环节 | 任何写操作必须过**7 区块确认卡片**；30 秒不确认**不落账**、收进待确认列表；撤销 = 反做单（不删原单） |
| 口音怎么办 | 不追求 100% 识别率，主打「**听不懂会问你，改一次就记住**」：置信度分级 + 数字归一 + 个人别名本 + 最多 2 轮澄清 + **全程按钮/数字键盘降级路径** |
| 要不要多租户 | **要，从第一天做**：数据模型多租户、产品体验单商户；共享表 + `tenant_id` + 隔离机制（云托管数据层方案见架构 §4.5），MVP 只暴露 1 商户 1 主仓。**所有客户同一入口，隔离靠登录态，不是一人一域名** |

**最反直觉但最重要的一条**：这个产品的毛利不由 AI 单价决定，由**「规则层命中率」**决定。模板命中率每提升 10 个百分点，单条命令成本近似线性下降；所以「用户教系统说话」不只是体验功能，是**降本基建**。定稿后毛利还要再扣一层**渠道抽成**（见 §5.4）。

## 1. 逐问速答

### Q1 · 「轻量化」到底轻在哪

保留最小闭环：商品档案 → 采购入库 → 销售出库 → 销退/采购退 → 库存/盘点/损耗 → 应收应付收付 → 3~5 张核心报表 → 导出。

明确砍掉：生产/BOM、审批流、总账凭证与结账、复杂成本核算、多级集团组织、CRM/促销引擎、多币种、自定义报表设计器。

> 判断标准：**任何需要用户「先配置再使用」的功能，MVP 一律不做。**

### Q2 · 给「懒人 / 电脑不熟练」的人，设计上要让步什么

- 不要求学任何命令语法，系统把口语翻成账（「拿走了」「拉来了」「记账上」都要能懂）。
- 高频、短、随身的动作放手机小程序；复杂、批量、高风险、要看全貌的放**电脑版微信里同一小程序的大屏管理页**——不做网页版、不记网址、不用账号密码，装了微信就行。
- **不承诺 100% 识别**，首次引导 3 句示范（进 / 卖 / 查）+ 教「说短句」+ 明示降级路径。
- 确认卡片支持「改一下」用**大图标点选 + 大号数字键盘**，不依赖拼音打字。
- 主确认按钮拇指热区 ≥ 88×88 px，按钮文案带关键值（「确认入库 2 箱可乐 ¥70」）而非裸「确认」。
- **电脑端大屏代价要认**：导出文件不能一键下载，改为「生成后转发到微信文件传输助手 / 保存到微信」；需 `resizable` + 双栏适配；部分 API 有 PC 端差异、Mac 基础库版本与电脑端麦克风可用性均**需核实**。

### Q3 · 小程序语音按钮与交互

「按住说」+「点一下说」双模式；明显开始/结束音；前端倒计时；锁屏/后台不启动。闲聊/误触给友好提示 + 3 个示例按钮，不扣次、不调 AI。

### Q4 · 命令体系（核心）

| 维度 | 规模 | 明细位置 |
|---|---|---|
| 业务域 | 12 | 采购入库、销售出库、销退/采购退、盘点损耗、调价、库存查询、单据查询、客户供应商、应收应付、商品档案、报表、系统辅助 |
| intent | 38 | `01-PRD.md` §2.8 命令清单表（含触发句式、槽位、必填、缺省、风险、确认策略） |
| 槽位 | 18 | `P Q U UP TA C S D N PS W AMT DOC TF TV EF ALIAS RATIO`；**`CTX` 为「上下文继承」内部标记（`is_slot:false`，不进用户话语解析结果），故槽位严格 18**，定义见 `slots.json.internal_markers` |
| 风险等级 | R0 只读 / R1 常规写 / R2 重点确认 / **R3 禁止语音直接执行** | 赊账、退货、盘点设定、调价、收付、抹零、跨日、撤销归 R2 |
| 确认策略 | C0 直接返回 / C1 大按钮 / C2 卡片+二次语音（带按钮兜底）/ **C3 语音仅发起 → 电脑版微信大屏管理页 + 老板二次确认执行** | 不再是「PC Web」 |

**已覆盖的复杂说法**：一句话多商品（拆多行共一张卡）、一句话多命令（P0 只保 1 写 + 1 读）、连续多轮录单（继承上单客户/日期/付款状态，但**每条仍独立确认**、继承值显式展示）、指代消解（「再来两箱」「还是那个客户」）、「按老价」（必须显示数值与来源日期）、单位换算（箱→瓶双显、无系数不臆造）。

### Q5 · AI 成本（你问的「限时间 / 排非命令 / 再给 AI」）

**答案：是，但要拆成六层漏斗，而且「规则层优先」才是最大省钱点。**

```
按下按钮
 G0 误触门禁          0 成本  锁屏/后台不启动、<1.5s 重复短音去重
 G1 时长与 VAD 门禁    0 成本  0.8s ≤ T ≤ 15s（硬 20s）、静音 700~900ms 判停、端点前留 300ms
  ↓ 通过才送 ASR（唯一外部成本入口；音频走对象存储临时上传，不走 callContainer 传二进制）
 G2 非命令过滤器      0 成本  静音/纯语气词/业务动词白名单/闲聊关键词/静态意图/60s 文本去重
  ↓ 疑似命令才继续
 G3 规则/模板层       0 LLM   18 个高频模板 + 个人词表 + 槽位抽取 + 12 类冲突检测 ★最大省钱点
  ↓ 未命中 / 冲突 / 多商品 / 模糊指代 才升级
 G4 LLM 兜底          计费    固定可缓存 prompt + Top20 商品 + 个人词表 + 最近 3 条上下文 + 紧凑 JSON
 G5 澄清状态机        0 成本  ≥0.85 直出 / 0.6~0.85 高亮追问 / <0.6 不出写卡；最多 2 轮、一次只问 1 槽
 G6 确认卡片          0 成本  7 区块 + 影响预览（只读预演，绝不写库）
```

**关键参数（全部建议值，需压测校准）**

| 参数 | 值 | 参数 | 值 |
|---|---|---|---|
| 录音上限 | 15s（硬 20s） | 最短有效 | 0.8s |
| VAD 判停 | 静音 700~900ms | 防吞字 | 端点前留 300ms |
| 澄清轮数 | 上限 2 | 同文本去重 | 60s |
| 连续录单态空闲 | 60s 退出清 CTX | 确认卡片 TTL | 30s（不确认不落账） |
| Prompt 注入 | 常用 Top20 + 个人词表 + 最近 3 上下文 | 严禁 | 注入全量商品档案 |
| 规则层命中率目标 | ≥45% | 无意图过滤率目标 | ≥90% |
| 单条命令综合成本目标 | ≤¥0.02（需核实） | 租户配额 | 30 次/分、1000 次/天 |

**成本公式（符号化，报价需核实）**

```
C_llm = T_sys×c_cache + (T_ctx+T_utt)×c_in + T_out×c_out
C_cmd = C_asr/p_card + (1 − p_tpl)×C_llm + k̄×C_clarify + C_infra
```

代入 PRD 假设值（C_asr ¥0.004、C_llm ¥0.02、p_tpl 45%、p_card 0.9）→ **C_cmd ≈ ¥0.0154**；`p_tpl` 降到 30% → ¥0.0184（+19%），升到 60% → ¥0.0124（−19%）。结论：**规则层命中率是毛利第一杠杆**。`C_infra` 在云托管形态下还需摊销外挂数据库/缓存与对象存储临时音频（**需核实**）。

**10+ 条降本手段**：端侧门禁、非命令过滤、规则层优先、prompt 缓存与注入预算、紧凑 JSON + `max_tokens`、60s 去重、澄清封顶、静态意图零 LLM、ASR 热词注入别名本、纠正回流扩模板、模型降级、长任务异步化、音频直传对象存储避免容器带宽与 100KiB 拆包。

**计费口径（信任设计）**：1 次有效语音记账 = **成功生成确认卡片**的录音；闲聊、环境音、误触、解析失败、用户取消 **一律不扣次**；`usage_ledger` 唯一约束保证幂等；超额**降级而非断服**（保留规则层 + 数字键盘，历史数据可查可导出，**不拿数据当人质**）。**付费额度来自虚拟支付发货，语音消耗来自 `usage_ledger`，两者分离**。

### Q6 · 确认环节

| 项 | 设计 |
|---|---|
| 卡片 7 区块 | ① ASR 原文（可重说/编辑）② 意图中文名 ③ 槽位表（每格标 `直接识别/缺省补全/换算得到/按你的习惯/待确认`）④ 计算式（2 箱 × 35 = 70）⑤ **影响预览**（8 箱 → 10 箱、应收 +460 未结）⑥ 风险条 ⑦ 大按钮 |
| 原文与结构化并列 | 凡被补全/换算/词表命中的字段加角标与浅色底，用户扫一眼就知道系统替他补了什么 |
| 超时 | 30s **不确认即不落账**，收进「待确认」列表；二次语音确认 15s 超时同样不执行；**禁止「沉默即同意」** |
| 二次确认 | R2 场景（赊账/退货/盘点/收付/低置信）触发 C2：朗读回读关键金额 + 请说「确认/取消」，**必须保留按钮兜底**；电脑版微信端依赖麦克风（需核实），**按钮兜底为默认路径** |
| 大屏适配 | 电脑版微信双栏（左原文+槽位、右影响预览+操作区），**7 区块信息一项不减** |
| 编辑 | 卡片内编辑**实时重算金额与影响预览，不重新调 AI** |
| 撤销 | 确认后 10 分钟内一键「撤」；**反做单**（不删原单、留痕可审计）；已被后续单据引用则禁止直接撤 |
| 影响预览安全性 | 走**只读库连接** + 纯函数 `simulate()`，DB 层无写权限；落账时 CAS 校验版本，并发变更则卡片标「已过期，请重新确认」 |

### Q7 · 口音与识别

| 层次 | 对策 |
|---|---|
| ASR 选型 | 必选：中文方言鲁棒、**词级 confidence**、**热词/自定义词表**（注入个人别名本，在 ASR 阶段就纠正）、一句话识别（能力均需核实）；用适配器隔离供应商 |
| 置信度 | ≥0.85 直出；0.6~0.85 出卡+高亮追问；<0.6 **不出写操作卡片**；词级取槽位覆盖区间**最小值**（保守）；无 confidence 时用规则构造代理置信度 |
| 数字金额 | 归一表（两/俩/仨、三十五、一百二、两块五、幺/拐/勾）；「一百二」按 120 但**高亮让用户核**；「三五」不自作主张；所有归一结果生成计算式供验算 |
| 别名匹配 | **MVP 用归一化 + 编辑距离 + 拼音 + Trie/AC 自动机**（0 成本、可解释）；向量检索 P2 再评估——候选集 <500 条、别名是字面/读音相似而非语义相似，embedding 每次还要花钱 |
| 多候选 | Top1−Top2 分差过小 → **出候选卡片点选，绝不自动选第一个**；选择即回流个人词表 |
| 澄清 | 一次只问 1 个最关键槽位 + 2~3 个可点选项，方言友好短句，话术**静态配置不调 LLM** |
| 闭环 | 卡片「改一下」的差异 → 个人词表 **1 秒内生效**（热缓存 + DB 双写，词表版本号击穿解析缓存）→ 下次 ASR 热词/规则层直接命中 → 一次成功率↑、澄清轮数↓、LLM 调用↓ → **越用越准、越用越省** |
| 兜底 | 2 轮仍不足 / ASR 连续失败 → 转大号数字键盘 + 常用商品点选网格，**不调 AI**；产品话术「听不懂会问你，改一次就记住」 |

### Q8 · 定价（v1.1 已按虚拟支付规则重做）

> **定稿：不是「包月自动续费订阅」，是「一次性购买 30 天权益 / 语音加油包」的道具直购。** 会员订阅（连续扣费）准入门槛为首次发布 ≥90 天 + 近 30 天日均 DAU ≥1 万，MVP 达不到；官方客服明确「一次性购买会员」直接接虚拟支付即可。

| 权益道具 | 目标 | 语音额度（假设） | 建议价（需核实） |
|---|---|---|---|
| 免费版 | 先试试的懒人商家 | **每 30 天 100~200 次** + 首期 +100（与 30 天权益周期对齐；用量按自然月归集，需核实） | ¥0 |
| 30 天权益·基础 | 夫妻店 / 便利店 | 600~1000 次 / 30 天 | ¥9~19 |
| 30 天权益·专业 | 批发档口 / 高频商家 | 2000~3000 次 / 30 天 或公平使用 | ¥29~49 |
| 30 天权益·门店版 | 2~10 家小连锁 | 按门店阶梯叠加 | ¥79~199 起 |
| **语音加油包**（主要增值点） | 春节/开学备货旺季 | 如 500 次（假设） | 如 ¥5（假设，需核实） |

**为什么不纯按次**：纯按次会抑制「想到就说」这个核心心智，用户每说一句都在算钱等于自废武功；一次性买 30 天给小微商家最在意的**预算确定性**；额度只是成本护栏与防滥用手段。购买入口**只在小程序内**（含电脑版微信），不得引导外部付款。

**到期提醒靠自有推送**（订阅消息能力**需核实**），不靠自动扣费；**留存模型从「续费率」改为「复购率 / 到期回购率」**，比原订阅模型更保守。

**毛利逻辑（已计入渠道抽成）**

```
单商户 30 天毛利 = 权益售价 × (1 − 渠道抽成率)
                 − 有效语音次数 × 单次综合解析成本
                 − 分摊固定成本
```

官方「虚拟支付：个人」页明示 Android 等 **1%**、iOS **12%**（Apple 佣金）；企业/个体户费率**需核实**。按 iOS 用户占比 40%（假设）粗算混合渠道成本 ≈ **5.4%**。PRD 6.6 原设「毛利率 70%」是**未计抽成的旧假设，需下调重算**。免费额度与权益价必须由「规则层命中率」和「渠道抽成」两个杠杆共同反推校准。

**三条可传播话术**：①「废话不收钱」②「模板能听懂的，不叫 AI」③「失败不扣次，改一次记一辈子」。对外只讲计费口径，不讲单价与成本——卖点是「聪明」不是「便宜」。

**不做**：不卖广告、不卖账目数据、不做金融导流；**不做自动续费（MVP 不达标）、不引导外部付款、不靠「官网更便宜」绕 iOS 抽成**。

### Q9 · 多租户

**结论：要做，但做「轻量多租户」—— 数据模型多租户，产品体验单商户。**

| 项 | 决策 |
|---|---|
| 隔离方案 | 共享表 + `tenant_id` + 数据库强制隔离 + 应用全局 scope 双保险。**微信云托管不内部署有状态服务**，数据层有 A/B/C 三方案（外挂托管 PostgreSQL 保留 RLS 为推荐；云开发数据库需改用应用层强制 scope + 安全规则 + CI 扫描 + 越权单测，隔离强度下降需如实标注）——详见架构 §4.5 |
| 备选对比 | 分 schema：运维重、DDL 需遍历；独立库：成本高、故障半径小，留给 P2 大客户（连接路由层切换，业务代码不改） |
| 模型 | `Tenant → Store → Member → Role`；商品档案/客户供应商**租户级共享**，库存/单据/盘点/损耗**门店级**，个人词表**员工级** |
| 防串账九道防线 | RLS + FORCE（方案 A）/ 安全规则（方案 B）、ORM 事件钩子自动注入、异步 Job 强制携带 tenant_id（最易漏点）、缓存 key 前缀 `t:{tenant_id}:`、对象存储路径前缀、唯一索引以 tenant_id 打头、CI 静态扫描「未带 tenant_id」、两租户两门店越权单测、审计巡检 |
| 登录与隔离 | **同一入口、同一 AppID**，微信身份（openid/unionid → tenant_id）带出租户；**不做账号密码、不做「一客户一域名」**（域名与租户隔离毫无关系，N 个域名 = N 次备案 N 张证书） |
| MVP 暴露 | 只建 1 Tenant / 1 Store、简化角色（老板/店员），UI 不出现「组织/门店」概念；升级多门店一键挂到总店 |
| 数据主权 | 老板随时全量导出（Excel/CSV，**文件经微信转发，不做网页下载**）；销户在电脑版微信大屏管理页申请 → 7 天冷静期（需核实合规）→ 物理删除含录音原文与备份 → 出具删除回执；卖点「**账是你的，随时能全带走**」 |
| 音频留存 | **MVP 默认不留存音频**，只留 `asr_text` + 结构化结果 + 置信度；降低合规与存储成本；排障可开关式加密留存 7 天（需核实） |

## 2. MVP 边界与实施顺序（v1.1）

**第一个版本做**：一个商户、一个主仓、1~2 人，手机小程序语音说一句话记「进 / 销 / 退 / 盘 / 查 / 收」，看一眼确认卡片、按一下大按钮落账；记错 10 分钟内能撤；**电脑版微信里打开同一个小程序**，在大屏管理页看账、改档、审批、导出（经微信转发）。8 个业务域 + 系统辅助约 17~20 个 intent。

## 4. 上线前置：域名、备案与 HTTPS

**结论（v1.1 已定稿）：走路线 B —— 微信云托管 + D 方案，正式上线不需要自有域名、不需要 ICP 域名备案、不需要自购 HTTPS 证书。**

| 后端形态 | 要不要自有域名 / ICP 备案 |
|---|---|
| A. 自建服务器 / 云函数 + 对外网页（**仅作备选，本次不做**） | **要**。小程序服务器域名、PC 网页、支付回调都指向自己的域名，须备案 + HTTPS |
| B. **微信云托管，且只服务小程序（已定稿）** | **不要**。官方明确：小程序经 `callContainer` 私有协议调用「无需域名，从而一开始就无需申请域名，也无需备案」。⚠️ 只有「在小程序/公众号之外**对外提供 API**」（网页版、第三方对接、品牌官网）才需要绑定已备案自定义域名；**支付回调不在此列**（见 §5）。收款必要条件见 §5，**与域名无关** |

**ICP 备案是什么**：域名指向中国内地服务器、对外提供互联网信息服务前，需向省通信管理局登记主体信息并取得备案号；未备案成功前不得开通访问，法定审核 20 个工作日。它备的是「域名 + 境内服务器」这一对，不是备小程序，也不是备客户数据。**本方案没有自有域名，因此这一项整体不适用。**

**别和「小程序备案」搞混**：小程序备案是对小程序本身（AppID、主体、服务内容）的备案，经微信公众平台提交，所有上线小程序都要做、不收费（**需核实**）；它和域名 ICP 备案是两件事。云托管免掉**后者**，免不掉**前者**——**小程序备案必做，且是上线与开通支付的前提**。

依据：微信小程序官方《网络》《域名管理》、微信云托管《开发常识》《自定义域名》《PC 小程序接入指南》、微信支付官方《开发接入准备》《回调通知注意事项》、工信部/接入商 ICP 备案说明（2026-11-15 检索）；平台规则会变，**以最新官方文档为准**。

### 哪些场景仍会要域名（仅路线 A；本方案不适用）

| 场景 | 要求 |
|---|---|
| 小程序所有网络请求（`wx.request` / `uploadFile` / `downloadFile`） | **路线 A**：只能访问后台配置的「服务器域名」，必须 HTTPS、**不能用 IP 或 localhost**、域名须经 ICP 备案；**路线 B**：走 `callContainer`，无需配置。音频/导出用 `wx.cloud.*` 系列（环境 ID）同样无需配置合法域名，**禁用 `wx.uploadFile`** |
| PC 管理端（**网页版**） | 托管于中国内地服务器需 ICP 备案；即使不绑域名、直接用 IP 对外访问也需要备案。**本方案不做网页版，无此项** |
| 微信支付回调（**自建服务器**） | `notify_url` 须商户自备公网 HTTPS 域名，国内服务器先完成 ICP 备案 |
| 微信支付回调（**云托管**） | **不需要自有域名**：云托管《微信支付》封装经微信私有链路把支付/退款结果推给指定服务（`callback_type:2`），《消息推送》走内网链路；本项目订阅走小程序虚拟支付，发货推送见 §5 |
| 小程序支付的「支付授权目录」 | **小程序不校验、无需配置**（仅 JSAPI / 公众号支付需要） |
| PC 端微信扫码登录（仅网页版需要） | 涉及网页授权回调域名，要求已备案域名；**本方案用微信登录，无此项** |

### 什么时候可以暂时不要

| 阶段 | 可行做法 |
|---|---|
| 本地开发 / 单元测试 | 小程序开发者工具勾「不校验合法域名」；后端走本机或云托管测试环境 |
| 内部演示 / 小范围内测 | 云托管默认环境；**默认公网域名仅供接口测试，勿用于正式生产，小程序后台也无法配置它** |
| 正式上线（路线 B） | 云托管 + `callContainer` 私有协议，**可关闭公网访问杜绝 DDoS**；免域名、免 ICP 域名备案、免证书、免配服务器域名 |

**改用云托管的四个硬限制（v1.1 架构已逐条修订）**

1. **默认公网域名不能用于正式生产**；云托管暂不支持域名备案功能（本方案不需要）。
2. **不支持在云托管内部署数据库 / Redis 等有状态服务** → 外挂托管 PostgreSQL（保留 RLS）或改云开发数据库（隔离强度下降，需补应用层与测试防线），见架构 §4.5。
3. **容器不持久化**，文件必须走对象存储；**`callContainer` 文本请求 100KiB 硬限制**（官方另一处列二进制 20MiB、超时 15s / 60s 两种口径，**需核实用哪个**），《开发常识》明确「请求中不建议包含图片，可通过对象存储处理」→ 音频改为「`wx.cloud.uploadFile` 直传对象存储 → 临时 fileID → 服务端只传引用」，见架构 §2；用 `wx.cloud.*` 不引入合法域名（已核实）。
4. **1 个自定义域名对应 1 个服务**（本方案不用自定义域名，暂不受限）。

> **2026-11-15 二次核实更正（保留）+ 三次核实收口**：上一版曾写「订阅收款可能把域名/备案拉回来」——结论是**不会**：云托管官方提供私有链路的支付回调与消息推送，开发者不需要自建 `notify_url` 域名。第三次核实进一步确认：官方《消息推送能力处理小程序虚拟支付回调》明确虚拟支付 `xpay_*` 事件由**云开发云函数消息推送**接收（推送模式「云函数」，事件含 `xpay_goods_deliver_notify` / `xpay_refund_notify` / `xpay_complaint_notify` 等），**发货回调锁定该路径，云托管消息推送不作为虚拟支付发货路径**；这不改变 D 方案主体形态，也不需要任何自有域名。⚠️ 社区旧文章「云函数需开 HTTP 访问服务 + 建议配自定义域名」是早期绕路方案，不应据此把域名写回来。

### 时间线（本方案真正的关键路径）

**不是 ICP 备案，而是「小程序备案」**：平台初审 1-2 工作日 → 工信部 12381 短信核验（**24 小时内**完成）→ 省通信管理局 1-20 工作日；**不收费、不支持加急**；状态「已备案」后才能开通支付、也是上线前提。

```
主体注册（企业/个体户）→ 微信认证 → 【立刻提交小程序备案】← T01 并行启动
   ↓ 备案通过后
开虚拟支付（资料审核 1-7 工作日 + 签约 1-2 工作日）→ 建道具 → 开 iOS 支付
   ↓
T05 联调时：下单 / 发货推送 / 查单兜底 / 额度发放全链路可用
```
> 备案未下来 **不能开通支付、不能上线**；微信认证与 iOS 支付开通的时长 **需核实**。T01~T04 的开发不依赖支付能力，可并行。

### 上线清单（路线 B · 本方案）

**主体注册 → 微信认证 → 小程序备案 → 建云托管环境与服务 → 小程序虚拟支付开通 + 道具配置（§5）→ 发货回调/消息推送 → 提审发布。全程不需要注册域名、不需要 ICP 域名备案、不需要自购 HTTPS 证书、不需要配服务器域名。**

## 5. 收款前置：小程序虚拟支付（与域名无关）

> **已定稿结论：D 方案不冲突，收款不会把域名和备案带回来。** 域名/备案不是收款的必要条件；但收款通道要换成「小程序虚拟支付」，并且有 3 个代价会改变定价模型（2026-11-15 核实，平台规则会变，上线前复核）。

### 5.1 为什么不是普通微信支付

《微信小程序平台运营规范》2.5.13：小程序内提供的**虚拟商品**（虚拟代币、解锁功能、订阅内容、付费功能、打赏、虚拟礼物等），**购买和支付均需接入小程序虚拟支付**；**不得引导至 App、公众号、H5、个人号、网站完成支付**。软件订阅属于「付费功能 / 订阅内容」→ 必须用 `wx.requestVirtualPayment`，**不能**自己用普通微信支付商户号 `wx.requestPayment` 收订阅费。违规处理：限期调整，否则阶梯封禁「iOS 支付接口 / iOS 用户搜索小程序 / iOS 用户打开小程序」。

### 7.3 不变的铁律（v1.1 全部保留）

1. 任何写操作必经「结构化回显 → **确认卡片 → 人确认 → 落账**」；只读不占卡片；影响预览只读预演（只读连接 + 纯函数 + CAS）；撤销 = 反做单不删原单。
2. 解析 = 端侧门禁 → 非命令过滤 → 规则/模板层优先（不调 LLM）→ LLM 兜底 → 澄清状态机 → 确认卡片；AI 只做歧义消解、多商品拆分、模糊指代。
3. 计费口径 = 成功生成确认卡片的录音；闲聊/误触/失败/取消不扣次；超额**降级不断服**，不拿数据当人质。
4. 多租户从第一天做；**数据模型多租户、产品体验单商户**；MVP UI 不暴露门店/组织概念。
5. 毛利第一杠杆是**规则层命中率**（目标 ≥45%），「用户教系统说话」是降本基建。
6. 数据真实性红线：**禁止编造真实竞品名称与价格**；所有价格/成本/阈值/费率/命中率标「假设，需核实」；平台规则定期复核。
