### 0.1 原始需求复述（逐字）

> "我需要做个轻量化的进销存，整个流程跟一般的进销存都差不多。只不过我想打的特色就是语音快捷输入。主要使用者我预想的就是一些很懒的商家或者一些执行电脑没有那么熟练的，但是还想用电脑管理自己的东西。移动端我觉得做成小程序就行，语音录入应该是比较大的按钮，点击输入各种命令，各种命令（要AI语音解析成各种操作命令）的考虑一定要全面。同时肯定要考虑语音AI成本，AI解析命令成本。是不是要限定时间，或者排除非命令，然后再给AI解析等等，这些都要你来帮我设计。还有语音输入肯定要确认的环节。还有是不是可能有一些语音口音的问题等等。最后再帮我想一个软件定价问题。还有这个软件是不是要做成多租户呢？等等"

## 1. 目标用户画像与核心场景

### 1.1 用户定位与核心洞察

| 维度 | 结论 |
|---|---|
| 主用户 | 小微商家：夫妻店、社区便利店、五金/建材/生鲜/水果摊、批发档口、小型批发商 |
| 典型特征 | 「懒」或「电脑不熟练」：拼音打字慢、看不懂复杂表格、记不住菜单层级、嫌流程长、手上常年在搬货/沾水/收钱 |
| 关键洞察 | 他们**不是不懂生意**，是**输入门槛太高**。语音的价值是「降低输入门槛」，不是炫技；一旦要学一套「命令语法」，产品就失败了 |
| 反直觉点 | 用户嘴上说的往往不是标准业务词（「拿走了」「拉来了」「退给他了」「记上」），系统必须把口语翻成账，而不是让用户学系统的话 |
| 使用环境 | 档口/仓库/摊位前，嘈杂、双手忙、单手操作手机、说话短促、方言重 |

### 1.2 「轻量化」到底砍掉什么（明确不做传统 ERP）

| 传统 ERP / 重量级进销存有的 | 本产品处理 | 理由 |
|---|---|---|
| 生产制造 / BOM / 委外 | **砍** | 目标用户不生产 |
| 多级审批流、工作流引擎 | **砍** | 一个人说了算，审批=增加负担 |
| 总账凭证、会计科目、结账封账 | **砍**（仅保留极简往来账） | 用户要「记个账」不是「做会计」 |
| 复杂成本核算（移动加权/先进先出/分批计价） | **弱化**：MVP 不暴露成本算法，仅按「进价/售价」记录 | 算不清就先不算，别挡住录入 |
| 多级组织架构、集团、跨法人结算 | **砍**（见第 7 节「轻量多租户」） | 超出小微商家 |
| CRM、会员、营销、促销引擎、复杂价格体系 | **砍** | 与「快捷记一笔」无关 |
| 批次 / 保质期 / 序列号 / 条码硬件深度集成 | **P2** | 生鲜档口后续可能需要，MVP 不铺 |
| 多币种、自定义报表设计器、开放 API | **P2 / 砍** | 保持轻 |
| **保留的最小闭环** | 商品档案 → 采购入库 → 销售出库 → 销退/采购退 → 库存与盘点/损耗 → 应收应付与收付 → 3~5 张核心报表 → 导出 | 「进销存账」四件事齐全即可 |

> 判断标准：**任何需要用户「先配置再使用」的功能，MVP 一律不做。**

### 1.3 端形态：一个小程序，两种屏幕

**定稿结论**：电脑端 = **电脑版微信里跑的同一个小程序**（`app.json` 配 `resizable` 开大屏适配，可双栏）；**不做独立网页版 / PC Web / H5 / Vite+React 工程**。原「PC 管理端」的全部职责由「小程序大屏管理页」承接：商品档案、别名本与说法训练、单据列表与更正、报表、用量与套餐、权限、R3 待办审批、数据导出。所有客户**同一入口、同一 AppID**；登录用微信身份（openid/unionid → `tenant_id`），**不做账号密码**（手机号 + 验证码仅作兜底，可 P1）；数据隔离靠登录态 + `tenant_id` + RLS，**绝不做「一客户一域名」**。

| 端形态 / 范畴 | 定位 | 主场景 / 主要能力 | 语音 | 明确不做 |
|---|---|---|---|---|
| ① **手机小程序**（同一 AppID 主入口） | **主录入端** + 轻量查看 | 语音大按钮录入、确认卡片、**查库存 / 查欠款 / 今日简报**、连续录单 | **核心能力，必须做到极致** | 批量建档、复杂权限、报表设计、数据导出 |
| ② **电脑版微信里的同一小程序**（大屏管理页） | **重度查看与管理** | 商品档案、别名本与说法训练、单据列表与更正、报表、用量与套餐、权限、**R3 待办审批**、数据导出、销户 | 电脑版微信端语音录入 P2 评估（**麦克风可用性需核实**）；C2 二次语音依赖麦克风时按钮兜底为默认 | 不与手机端追求对等交互；大屏需单独适配 |
| ③ **明确不做** | — | **独立网页版 / PC Web / H5 / Vite+React 工程 / 账号密码登录** | — | 见下文「为什么不做网页版」 |

**分工原则（写进产品原则）**

1. 高频、短、随身、要快的动作 → **手机小程序语音**；复杂、批量、高风险、要看全貌的动作 → **电脑版微信大屏管理页**。
2. **同一 AppID、同一微信身份、同一租户数据实时同步**；手机端确认落账，大屏管理页立即可见；不做「一客户一域名」。
3. **R3 高风险操作（2.7 白名单）的「最终执行」强制落在「电脑版微信管理页 + 二次确认」**，语音只能发起。
4. 用户可能**根本没有电脑**也能用（**手机小程序闭环完整**）；电脑版微信大屏是「升级选项」而非「必需项」——这直接回应「电脑不熟练」人群。

> **为什么不做网页版**：一个小程序承接全部职责后，可**免自有域名、免 ICP 域名备案（域名）、免 HTTPS 证书、免配服务器域名**，也免一整套账号密码登录体系（微信身份即登录态）；目标人群本来就装微信、只会微信，不必再学一套网页登录。后端走微信云托管 `callContainer` 私有协议，是这套「免域名」成立的前提（详见 `docs/00-决策速览.md` §4）。
>
> **代价（均需核实）**：① 导出不能像网页一键下载，改为「**生成文件后转发到微信文件传输助手 / 保存到微信 / 微信内预览分享**」（相关 API 可用性需核实）；② 大屏需单独适配（`resizable` + 双栏布局），确认卡片 7 区块一项不减（见 §3 大屏适配）；③ 部分 API 存在 **PC 端差异**、**Mac 基础库版本有限制**；④ **电脑端麦克风可用性有限制**，电脑端录音 API 需核实。

## 2. 语音命令体系（本项目最核心产出）

### 2.1 设计原则

1. **一句话 = 一张可确认的业务卡片**（或一个结构化候选）；永不「静默直接改账」。
2. **先结构化、再执行**：ASR 文本 → 意图 + 槽位 → 回显 → 人确认 → 落账。
3. **缺省优先、少问**：能按规则补全的（今天 / 现结 / 主仓 / 基本单位）不问用户；但**业务关键值缺失必须问**，绝不臆测。
4. **意图、业务域、风险等级、确认策略四者绑定**（见 2.7 命令清单表）。
5. **口语优先**：句式库必须来自真实档口说法，不用「请执行采购入库单」这种书面语。
6. **可被教**：用户每次纠正都变成下次的资产（见第 3.9 / 4.3）。

### 2.2 槽位字典（统一定义，命令清单表直接引用代号）

| 代号 | 槽位名 | 类型 | 说明 / 示例 |
|---|---|---|---|
| `P` | 商品 product | 实体引用 | 「可乐」「快乐水」「二中门口那家」（客户另见 C） |
| `Q` | 数量 quantity | 数值 | 「两箱」「三斤」「5 个」，归一为阿拉伯数字 |
| `U` | 单位 unit | 枚举 | 箱 / 件 / 瓶 / 斤 / 个 / 条 / 罐，需与商品档案换算表对齐 |
| `UP` | 单价 unit_price | 金额 | 「一件三十五」「每箱 24」 |
| `TA` | 总价 total_amount | 金额 | 「一共两百三」「合计 460」 |
| `C` | 客户 customer | 实体引用 | 「李婶」「兴旺超市」「二中门口那家」；缺省=散客 |
| `S` | 供应商 supplier | 实体引用 | 「老张」「南门批发老赵」；缺省=待补 |
| `D` | 时间 date | 日期 | 「今天」「昨天」「前天」「3 号」「上月」「上次」 |
| `N` | 备注 note | 文本 | 「没拆封」「有问题」「微信转的」 |
| `PS` | 付款状态 payment_status | 枚举 | 已结 / 未结（赊账）/ 部分；缺省=已结 |
| `W` | 仓库/门店 warehouse | 实体引用 | 「二号店」「主仓」；缺省=当前门店默认仓 |
| `AMT` | 金额 amount | 金额 | 收付款、抹零、欠款核销用 |
| `DOC` | 单据/对象 doc_ref | 引用 | 「昨天那张单」「3 号卖给李婶的单」「上一单」 |
| `TF` | 目标字段 target_field | 枚举 | 进价 / 售价 / 联系人 / 电话 / 名称 |
| `TV` | 目标值 target_value | 动态 | 「3 块 5」「兴旺超市」 |
| `EF` | 生效时间 effective_date | 日期 | 「从明天起」 |
| `ALIAS` | 别名 alias | 文本 | 「快乐水」「大绿棒子」 |
| `RATIO` | 换算系数 | 数值（内部） | 1 箱 = 24 瓶，由商品档案给出，**不可臆造** |
| `CTX` | 上下文继承 | 内部标记 | 连续录单时继承 C/S/D/PS/W |

### 2.3 缺省值规则表（解析层必须实现）

| 槽位 | 缺省值 | 触发条件与例外 | 回显要求 |
|---|---|---|---|
| `D` 时间 | **今天**（业务发生日） | 「昨天/前天/3 号/上月/上次」按相对时间解析；跨月跨年边界必须提示确认 | 显示解析出的**具体日期**，不显示「昨天」 |
| `PS` 付款状态 | **已结（现金/现结）** | 出现「欠着 / 挂账 / 没给钱 / 先记着 / 记账上 / 下回给」→ 未结；「付了 / 给了 / 微信转了 / 现结 / 扫码了」→ 已结；矛盾时以**最后明确表述**为准并提示 | 未结必须标黄提示 |
| `W` 仓库 | **当前门店默认仓 / 主仓** | 多门店时必须显式或继承上次，不得跨店猜测 | 显示门店名 |
| `U` 单位 | 商品档案**基本单位** | 出现「箱/件/条」等包装单位 → 按换算表折算到基本单位；**无换算表则澄清**，不臆造系数 | **双显**：原话「2 箱」＋换算「= 48 瓶」 |
| `C` 客户 | **散客 / 现金客** | 零售不强制建档；出现具体称呼则匹配别名本 | 显示「散客」也要显示，不能藏 |
| `S` 供应商 | **待补** | P0 不强制拦截录入，但卡片上标「供应商待补」并可一键补 | 明确标注 `待补` |
| `UP` / `TA` | 见冲突规则 | 「一件三十五」=单价；「一共两百三」=总价；「三箱两百一」=总价并反算单价；只给一个裸数字且无线索 → **澄清** | 展示计算式（2 箱 × 35 = 70） |
| `Q` 数量 | **无缺省，必须追问** | 「进了可乐」没数量 → 不问出来不落账 | — |
| `ALIAS` / 个人词表 | 优先命中个人词表 | 命中即填充并标注「按你的习惯」 | 显示来源标签 |
| `CTX` 上下文 | 连续录单态继承上一条已确认单的 C/S/D/PS/W | 换客户/换日期必须说出或系统提示；退出连续态即清空 | **显式展示继承值**，禁止静默继承 |

### 2.4 按业务域分类的口语句式（每域 ≥3 条，带方言/口语味）

> 说明：以下句式同时作为 **LLM few-shot 样例库** 与 **规则模板库** 的输入源。所有句式均为产品侧构造的业务样例，非引用外部语料。

#### 域 1 · 采购 / 入库（purchase）

- 「今天进了两箱可乐，一件三十五」
- 「刚到了 20 件娃哈哈，先欠着老张家的钱」
- 「啤酒拉了五箱，一共两百三，已经微信付了」
- 「上王老板那拿了三箱矿泉水，每箱 24」
- 「进点货：红牛一件、和其正两件，都按老价」

典型槽位：`P Q U UP|TA S D PS N`；**必填** `P + Q`（数量缺失必追问）；`S` 可待补。
特殊处理：「按老价」= 该供应商该商品最近一次进价，回显必须显示数值与来源日期；「拉了/到了/拿了/进了」统一判为入库增量。

#### 域 2 · 销售 / 出库（sales）

- 「卖了三瓶冰红茶，收了 12 块」
- 「刚才李婶拿走两条烟，一共四百六，说下回给」
- 「出库：娃哈哈一箱给二中门口那个店」
- 「今天卖了 5 斤苹果、3 斤香蕉，现金」
- 「那个……来福超市要十箱可乐，记账上」

典型槽位：`P Q U UP|TA C D PS N`；**必填** `P + Q`；`C` 缺省散客。
特殊处理：「拿走 / 发走 / 要 / 出库 / 卖了」= 出库；「记账上 / 下回给」= 未结应收。

#### 域 3 · 退货（销退 + 采购退）

- 「昨天那箱可乐退回来了，退他 35」
- 「客户退了两瓶，钱已经退给人家了」
- 「进的货有问题，退给供货商三箱，还没退钱」
- 「退：王老板上次那条烟没拆，拿回来了」
- 「二中店把上次那两箱退回来了，先挂着」

典型槽位：`P Q U C|S DOC D AMT PS N`；**必填** `P + Q + 方向(退给客户/退给供应商)`；方向判不出 → 澄清。
特殊处理：退货必须尝试关联 `DOC` 原单；「钱退了没」是**独立退款状态**，不等于货款结清；退货为 R2，必须确认。

#### 域 4 · 盘点与损耗

- 「盘点，仓库可乐还剩 8 箱」
- 「今儿盘了下，红牛对不上，少了两罐，记损耗」
- 「坏了三斤苹果，报损」
- 「货架上数了下，矿泉水 15 瓶」
- 「盘点：娃哈哈 3 箱、可乐 2 箱、红牛 0」

典型槽位：`P Q U W D N`；**必填** `P + Q`（盘点可 0）。
特殊处理：**「还剩 / 盘点是 / 实盘 / 数了下 / 一共就」= 快照设定库存**，产生盘盈/盘亏调整；「坏了 / 少了 / 报损 / 损耗」= 损耗单核减。二者与「再入 8 箱」的增量语义**必须区分**（见 2.5）。多商品盘点拆成多行共一张卡。

#### 域 5 · 调价

- 「可乐从明天起卖 3 块 5」
- 「娃哈哈进价改到一件 22」
- 「红牛零售价调到 6 块，批发价不动」
- 「以后膨胀螺丝按 8 块一个卖」

典型槽位：`P TF TV EF`；**必填** `P + TF + TV`；`EF` 缺省今天。
特殊处理：调价影响后续开单与历史报表口径，R2；「从明天起」需 `EF`；**改历史已发生单价禁止语音**（走更正单）。P1 落地。

#### 域 6 · 库存查询（只读）

- 「可乐还剩多少」
- 「查一下红牛今天卖了几件」
- 「仓库里矿泉水够不够 10 箱」
- 「哪些货快没了」
- 「二号店娃哈哈还有几箱」

典型槽位：`P Q U W D`；**必填** 无（能查就查，查不出给候选）。R0，直接返回结果，不写库、不占确认卡片。

#### 域 7 · 单据查询（只读）

- 「把昨天那张单子调出来」
- 「今天一共进了多少货」
- 「给我看上一单」
- 「查 3 号卖给李婶的单」
- 「上月老张那笔结了没」

典型槽位：`DOC D C|S P`；**必填** 无。R0。模糊时间「上次 / 那笔」须绑定最近一单并展示具体日期；跨月要提示。

#### 域 8 · 客户 / 供应商

- 「新客户，兴旺超市，联系人刘姐，电话 138 开头那个」
- 「把二中门口那家改叫'二中店'」
- 「供应商加一个：南门批发，老赵」
- 「李婶就是李桂花，以后都记一个本上」→ 合并（R3）
- 「给兴旺超市备注：每周三送货」

典型槽位：`C|S TF TV N`；**必填** `对象 + 名称`；电话等敏感字段建议**电脑版微信管理页**补录。
特殊处理：**合并 / 删除客户供应商 = R3，禁止语音直接执行**（连锁影响历史往来账）。

#### 域 9 · 应收应付与欠款收付

- 「李婶还了 200，还欠 260」
- 「把上月老张家的货款结了，给现金 1200」
- 「兴旺超市今天微信转了 500」
- 「查一下谁还欠我钱，一共多少」（只读）
- 「老王那笔抹个零，收 1180 就行」

典型槽位：`C|S AMT PS D DOC N`；**必填** `对象 + AMT`。
特殊处理：收款/付款 R2（钱相关，强制确认 + 建议二次语音确认）；「抹零 / 免了 / 不要了」= 核销，R2 起、超过阈值升 R3；欠款查询 R0。

#### 域 10 · 商品档案维护

- 「加个新品：元气森林白桃，进价 3 块 5，卖 5 块，一箱 15 瓶」
- 「可乐别名叫'快乐水'」
- 「以后'大瓶可乐'就指 2 升那种」
- 「娃哈哈一箱等于 24 瓶」→ 设换算（R3）
- 「这个商品不卖了，下架」

典型槽位：`P UP TA U RATIO ALIAS TF TV`；**必填** `P`。
特殊处理：**「下架/不卖了」= 停用，不是删除**；**设置换算系数 R3**（会连锁重算历史数量，语音只能发起、**电脑版微信管理页确认**）；别名新增属于「教系统」，命中即省 AI（第 5 节）。

#### 域 11 · 报表查询（只读 + 导出）

- 「今天赚了多少」
- 「这个月卖了多少钱」
- 「哪样货卖得最好」
- 「给我看本月的进销存」
- 「导出这个月的账」→ 导出 R3

典型槽位：`D P C|S W`；**必填** 无。报表结果 R0 直接返回；**导出动作 R3，语音仅生成待办，电脑版微信管理页二次确认后执行**。

#### 域 12 · 系统 / 辅助

- 「撤销」/「撤回刚才那一条」
- 「错了，重来」/「别记了，取消」
- 「帮助」/「你能听懂啥」/「举个例子」
- 「接着录」/「录完了」
- 「上一条改一下，可乐是三箱不是两箱」
- 「以后我说'拿一条'就是卖一条烟」

典型槽位：`DOC P Q TF TV ALIAS`；**必填** 视意图。
特殊处理：`sys.undo` 走反做单（R2 + 确认）；`sys.cancel` 不写库；`sys.continue` 进入连续录单态；`sys.teach` 写个人词表并即时生效；`sys.help/example` 纯静态内容，**不调 AI**（省钱）。

### 2.5 一句话多商品 / 一句话多命令 / 连续多轮录入的处理规则

| 场景 | 示例 | 处理规则 |
|---|---|---|
| **一句话多商品** | 「进了红牛一件、和其正两件、可乐三箱，按老价」 | 拆为 N 条**同类型明细行**，共用一张表头（`D / S / PS / W`）；回显为**一张卡片内多行表格**，金额逐行计算并给合计；支持「整张一次确认」或「逐行改后确认」；任一行槽位不全 → 该行标「待补」，不阻塞其他行；`按老价` 逐商品取各自最近进价 |
| **一句话多命令（写 + 读）** | 「卖了三瓶可乐，顺便查下还剩多少」 | 拆为「1 写 + 1 读」：写操作出确认卡片、必须确认；读操作确认后自动追加结果（或折叠展示），**不单独再确认**；**P0 只保证 1 写 + 1 读** |
| **一句话多命令（多写）** | 「卖了三瓶可乐，再进两箱红牛」 | **P0 拆成两张独立卡片依次确认**，不合并落账；P1 支持「一张单据多动作」但必须逐动作展示影响预览 |
| **连续多轮录入** | 点「接着录」→「红牛一件」→「可乐两箱」→「还是那个客户」→「录完了」 | 进入**连续录单态**：继承上一条已确认单的 `C/S/D/PS/W` 作为缺省；**每条仍独立回显确认**（不因连续而跳过确认）；显式「录完了 / 结束」或空闲超时退出；换客户/换日期必须说出或系统主动提示「还是记在李婶名下吗？」 |
| **指代消解** | 「再来两箱」「这个也来一件」「同上」「还是那个客户」 | 绑定到上一条已确认单的槽位；**回显必须显式展示继承来的值**（如「客户：李婶（沿用上单）」），禁止静默继承；无可靠上文 → 澄清 |
| **上下文边界** | 退出连续态 / 切换业务域（由「进」转「卖」） | 自动清空 `CTX` 并提示，避免把供应商误当客户 |

### 2.6 歧义与冲突清单（解析层判定规则）

| # | 冲突类型 | 示例 | 判定规则 | 兜底动作 |
|---|---|---|---|---|
| 1 | **改库存 vs 改数量（最危险）** | 「盘点，可乐还剩 8 箱」vs「再入 8 箱可乐」 | 「还剩 / 盘点是 / 实盘 / 数了下 / 一共就」→ **快照设定库存=8**（产生盘盈盘亏）；「进 / 加 / 再 / 补 / 入了 / 拉了」→ **增量 +8** | 判不出 → 澄清：「是把库存**改成** 8 箱，还是**再入库** 8 箱？」；两者都展示影响预览（8→8 vs 8→16） |
| 2 | **「卖了」vs「退货」** | 「卖了三箱」vs「退回来三箱」 | 「退 / 退回 / 拿回来了 / 不要了 / 有问题」→ 退货；「卖了 / 拿走 / 出库 / 发走 / 要」→ 销售 | 同句出现方向词 → 澄清方向（退给客户 / 退给供应商 / 客户退回） |
| 3 | **单位换算（箱/瓶/件/斤）** | 「两箱可乐」 | 以商品档案 `RATIO` 为准；回显**双显原话与折算值** | 档案无该单位换算 → **不臆造系数**，澄清「一箱是几瓶？」并把说法记入「待教学」，教学后生效 |
| 4 | **金额与单价混淆** | 「一件三十五」/「一共两百三」/「三箱两百一」/「可乐 35」 | 「一件/每箱/一斤 X 块」→ `UP`；「一共/总共/合计/收了」→ `TA`；「N 单位 + 金额」无「每」→ 判 `TA` 并**反算 UP**；裸数字无线索 → 澄清 | 反算结果必须在卡片展示计算式让用户验算 |
| 5 | **同名商品 / 别名歧义** | 两个规格都叫「可乐」 | 命中多个候选 → **出候选卡片点选**，不自动选第一个 | 选择结果回流个人词表，下次优先命中 |
| 6 | **模糊时间** | 「昨天」「前天」「上次」「上回」「月初」「那天」 | 相对时间解析为具体日期；「上次/上回」绑定该 `C/S` 最近一单 | 无法唯一确定 → 列 2~3 个候选日期点选；跨月/跨年边界主动提示确认；回显**必须显示具体日期** |
| 7 | **负数与撤销** | 「退 / 减 / 冲 / 撤销 / 删」「少了一箱」 | P0 **不允许负数量入库**；撤销走「反做单」而非录负数；「少了一箱」= 损耗，不是负销售 | 检测到负向语义 → 引导到 `sys.undo` 或 `stock.loss` |
| 8 | **数字读法** | 「两/俩/仨/幺/拐/勾」「三十五」「三五」「一百二」「两块五」 | 建归一规则表（幺=1、拐=7、勾=9 等口语/军语读法是否纳入**需核实**）；「三五」可能是 35 / 3.5 / 3 和 5，结合语境 | 不确定 → 回显计算式并追问；「一百二」按 120 处理但高亮让用户核 |
| 9 | **付款状态冲突** | 「欠着……已经付了」 | 以**最后明确表述**为准 | 回显提示「按你最后说的记为已结，对吗？」 |
| 10 | **「老价 / 老规矩」** | 「按老价」「按老规矩」 | 「老价」= 该对象+该商品最近一次成交价；「老规矩」= 该商户最近的 `PS/W` 组合 | 回显**显示具体数值与来源日期**，不静默套用；无历史 → 澄清 |
| 11 | **同音词** | 帐/账、进/近、售/收、箱/香、件/见、付/负、退/推 | 结合意图与槽位类型消解，不单独依赖 ASR 文本 | 回显一律用**业务词**（不展示同音错字） |
| 12 | **门店归属歧义（多门店时）** | 「可乐还剩多少」 | 默认当前门店；跨店查询必须显式说门店名 | 多门店且未指定 → 提示「查当前二号店，还是全部店？」 |

### 2.7 高风险操作白名单（禁止语音直接执行）

| 操作 | 风险原因 | 语音侧策略 | 替代流程 |
|---|---|---|---|
| 删除单据 / 清空库存 / 清空商品档案 / 批量删除 | 不可逆、账目灭失 | **禁止语音执行**；仅可「标记待删 / 发起申请」 | 语音发起 → 生成待办卡片 → **电脑版微信管理页（二次校验 + 老板确认）** → 留痕 |
| 改历史账（跨已对账日期、修改已确认单的金额/数量） | 破坏可审计性 | **禁止直接改** | 走「反做单 + 新建更正单」，原单永久保留 |
| 大额收付（单笔超阈值） | 资金损失 | 建议 **MVP 不开放**；P1 开放时强制「二次语音确认 + 金额朗读回读」+ 阈值可配（建议起始 5000，**假设，需核实**） | 超阈值一律转**电脑版微信管理页（二次校验 + 老板确认）** |
| 权限变更 / 新增员工 / 改角色 / 转移账目所有权 | 越权、数据泄露 | **完全禁止语音** | **电脑版微信管理页专属**，老板操作 |
| 商品合并 / 客户合并 | 连锁影响历史单据与往来账 | 语音仅发起 | **电脑版微信管理页**展示影响清单后确认 |
| 改换算系数 / 删除别名本 | 连锁重算历史数量 | 语音仅发起 | **电脑版微信管理页确认** |
| 结账 / 月结封账 | 影响全局口径 | 禁止语音 | **电脑版微信管理页专属** |
| 全量数据导出（含敏感账目） | 数据外泄 | 语音仅生成待办 | **电脑版微信管理页二次确认**后执行；导出文件经微信转发，不做网页下载 |
| 销户 / 删除租户 | 不可逆 | **完全禁止语音** | **电脑版微信管理页** + 冷静期（见 7.4） |

> **通用替代流程**：语音发起 → 生成「待办 / 待审批卡片」→ **电脑版微信管理页（二次校验 + 老板确认）**完成 → 全程留痕（谁、何时、做了什么）。

### 2.9 intent schema 字段建议（供架构师 / Prompt 设计直接采用）

每个 intent 建议包含以下字段，形成可直接消费的结构化定义：

```
intent_id        : 如 purchase.create
domain           : 12 个业务域之一
risk_level       : R0 | R1 | R2 | R3
confirm_policy   : C0 | C1 | C2 | C3
sample_utterances: 真实口语句式数组（≥3，来自 2.4）
slots[]          : { code, name, type, required, default_rule, validation, clarifier_template }
side_effect      : 影响的库存/应收应付/报表口径（用于生成「影响预览」）
reversal         : 是否可撤销 / 反做单规则
template_hit     : 是否可由规则层命中（true 则不调 LLM）
whitelist_blocked: 是否属于 R3 白名单
clarifier_templates: 该 intent 的低置信 / 槽位缺失追问话术
```

LLM 输出强制为**紧凑 JSON**（不输出解释文字），示例结构：

```json
{"intent":"purchase.create","slots":{"P":"可乐","Q":2,"U":"箱","UP":35,"S":"待补","D":"2025-11-15","PS":"已结","W":"主仓"},"source":{"Q":"asr","UP":"asr","S":"default","D":"default"},"confidence":0.91,"clarify":null}
```

> `source` 字段用于回显卡区分「直接识别 / 缺省补全 / 换算得到 / 待确认」（见 3.2），是确认环节与成本归因的关键。

## 3. 确认环节设计（用户明确要求）

### 3.1 原则

1. 语音天然不确定 + **账目不可静默改** → 任何写操作必须有一次人类确认。
2. 确认不是「添堵」，是**建立信任的仪式**：让用户看见系统听成了什么、将要改什么。
3. **省钱不省确认**：规则层命中（不调 AI）也照样出确认卡片。
4. 只读查询不占确认卡片，直接返回结果（保持「快」）。

### 3.2 解析结果回显卡片的信息结构（自上而下）

| 区块 | 内容 | 要求 |
|---|---|---|
| ① 原文区 | **ASR 原文全文**（可点「重说」/「编辑原文」） | 原文与结构化结果**并列展示**；ASR 置信度低时高亮 + 「可能没听清」标识 |
| ② 意图区 | 意图中文名 + 业务域图标（如「采购入库」） | 用户看得懂的业务词，不展示 intent 代号 |
| ③ 槽位表 | 商品 / 数量 / 单位 / 单价 / 总价 / 客户 / 供应商 / 时间 / 付款状态 / 仓库 / 备注 | 每格带**来源标签**：`直接识别` / `缺省补全` / `换算得到` / `按你的习惯` / `待确认`；被补全/换算的字段用不同底色 |
| ④ 金额与计算式 | 大写金额 + 计算式 | 如「2 箱 × 35 = **70 元**」「2 箱 → 48 瓶（1 箱=24 瓶）」「三箱共 210，折合每箱 70」 |
| ⑤ **影响预览** | 「执行后：可乐库存 8 箱 → 10 箱」「本单应收 +460（未结）」 | **最关键**：让用户看到后果，直接降低误确认与撤销率 |
| ⑥ 风险提示条 | 赊账 / 退货 / 盘点设定 / 调价 / 跨日 / 大额 / 低置信 | 黄（R2）/ 红（R3 拦截）条 + 一句人话解释 |
| ⑦ 操作区 | 【确认 · 绿 · 大按钮】【改一下】【取消 · 重说】 | 主按钮文字带关键信息：**「确认入库 2 箱可乐 ¥70」** 而非裸「确认」 |

**视觉/交互参数（建议值，需可用性测试校准）**

- 主确认按钮：拇指热区 ≥ **88×88 px**（最小触控目标不小于 44pt），置于屏幕下半部单手可达区。
- 三按钮不并列等宽：确认占主导，改一下/取消为次要，避免误点。
- 卡片一屏内尽量不滚动即可看到「槽位表 + 金额 + 影响预览 + 确认按钮」。

**大屏适配（电脑版微信，v1.1 新增）**

- 电脑版微信下确认卡片可用**双栏布局**：左栏放「① 原文区 + ③ 槽位表 + ④ 金额与计算式」，右栏放「⑤ 影响预览 + ⑥ 风险提示条 + ⑦ 操作区」，② 意图区置于顶部通栏。
- **7 区块信息一项不减**：双栏只是重排，不删字段、不折叠来源标签、不省略计算式与影响预览；手机端单栏与大屏双栏共用同一套卡片数据结构。
- **C2 二次语音在电脑端依赖麦克风可用性**，电脑端麦克风可用性 / 录音 API 存在差异（**需核实**）；因此**按钮兜底必保留且为默认路径**，不得强制只靠语音（与 3.5 一致）。
- 大屏由 `app.json` 配 `resizable` 开启；PC 端 API 差异与 Mac 基础库版本限制（**需核实**）不得影响卡片信息完整性。

### 3.3 原文与结构化结果并列

- 采用「上原文 / 下结构化」或左右对照；**差异字段高亮**：凡结构化里被「缺省补全 / 换算 / 词表命中」得到的值，用角标 + 浅色底标注来源。
- 目的：用户可以**只用眼睛扫一眼**就知道「系统替我补了什么」，这是口音/缺省场景下信任的关键。

### 3.4 大按钮确认

- 一次点击即落账，无二次弹窗（C1 场景）。
- 按钮文案动态生成、携带关键槽位，降低「看都没看就按」的误操作。
- 落账后给**轻量成功反馈**：「已记：进 2 箱可乐 ¥70」+ 库存变化小字 + 「撤」入口（见 3.8）。

### 3.5 二次语音确认（C2）

| 项 | 设计 |
|---|---|
| 触发条件 | R2 意图、金额超阈值、ASR/解析置信度低、盘点快照设定、抹零/核销、退货涉及退款 |
| 话术 | 「请说**确认**或**取消**」＋ **朗读回读关键金额**：「确认入库两箱可乐，共七十元」 |
| 兜底 | **必须同时保留点击按钮兜底**（嘈杂环境/口音重时说不出「确认」也能完成），不能强制只靠语音 |
| 失败处理 | 二次语音未识别 / 识别为「取消」→ 不落账，卡片回收到「待确认」列表，不丢 |
| 禁止 | 二次确认不得自动超时执行（见 3.6） |

### 3.6 超时策略

| 参数 | 建议值 | 理由 |
|---|---|---|
| 确认卡片停留时长 | **30 秒**（可配 15~60s） | 够看一眼 + 按一下；太长占屏、太短来不及 |
| 超时默认行为 | **不确认即不落账**（安全优先） | 账目类绝不能「沉默即同意」 |
| 超时后 | 卡片收进「**待确认**」列表，用户随时回来处理，不丢数据 | 忙时被叫走是常态 |
| 二次语音确认超时 | 15 秒，超时回收，不执行 | 同上 |
| 连续录单态空闲超时 | 60 秒自动退出并清空 `CTX` | 防止把下一单错误继承到上一个客户 |
| 长录音硬上限 | 15 秒（见 5.2） | 与超时策略联动 |

> 参数均为**建议值，假设，需按真实可用性测试校准**。

### 3.7 确认前的可编辑项

| 槽位 | 编辑方式 | 照顾「不打字」人群 |
|---|---|---|
| 商品 | 点选搜索 / **常用商品本 Top20** / 别名本 | 大图标网格，不要求输入文字 |
| 数量 / 单价 / 金额 | **大号数字键盘** | 不依赖拼音、不依赖语音 |
| 单位 | 下拉（箱/瓶/件/斤/个） | 选择即触发换算重算并双显 |
| 时间 | 日历控件 | 避免手输日期 |
| 付款状态 | 三段开关：已结 / 未结 / 部分 | 一眼可切 |
| 客户 / 供应商 / 仓库 | 常用列表点选 | 支持「待补」后补 |
| 备注 | 可选，语音或点选常用备注 | 非必填 |

**规则**：编辑后**实时重算**金额与影响预览；**编辑不重新调用 AI**（省钱 + 即时反馈，见 5.3）；编辑差异进入纠正回流（3.9）。

### 3.8 撤销窗口与「反做单」

| 项 | 设计 |
|---|---|
| 撤销窗口 | 确认后 **10 分钟内**可一键「撤」（可配，建议值/假设）；超时或已对账则走更正流程 |
| **反做单** | **不删除原单**：生成一笔等额反向单 + 关联原单号 + 记录（谁、何时、为什么撤）→ 账可审计、可对账 |
| 超过窗口 | 不能简单撤；走 `sys.correct`（**第一步反做原单，第二步用户重说一句落更正单**）或**电脑版微信管理页**处理 |
| 已被后续单据引用 | 禁止直接撤，提示「这笔已被后面的单引用，请走更正或到电脑处理」 |
| 撤销本身 | 是写操作 → **也要二次确认**（C2），并展示反做后的库存/账目影响 |
| 产品话术 | 「撤的不是数据，是一笔**可追溯的冲正**」——让小微商家也敢用、不怕点错 |

### 3.9 错误纠正回流成个人词表（闭环）

**回流什么**：用户在确认卡片上「改一下」产生的每一处差异，以及二次确认时被否决的解析结果。

| 差异类型 | 回流内容 | 下次效果 |
|---|---|---|
| 商品别名 | 原文片段 → 正确商品 | 「快乐水」直接命中可乐，`按你的习惯` 标注 |
| 单位换算 | 「一箱=24 瓶」类说法 | 补齐换算表（设置换算系数本身走 R3，须在**电脑版微信管理页 / 说法训练页（大屏）**确认，但**说法**先进词表） |
| 数字读法 | 「幺/两/俩/三五」→ 数值 | 归一优先命中个人词表 |
| 客户/供应商简称 | 「二中门口那家」→ 兴旺超市 | 简称直达 |
| 缺省偏好 | 该商户 90% 现结 / 常用某仓 | 缺省值个性化（需达频次阈值） |
| 常用商品 | 被频繁录入的商品 | 置顶 Top20，确认卡片选择更快 |

**分层与治理**

```
个人词表（本商户/本员工，最高优先）
   ↓ 用户显式开启 + 脱敏后（可选）
行业通用词表（平台沉淀，跨租户，需脱敏）
   ↓
全局基础归一表（数字读法、通用口语）
```

- **命中即不调 AI 或降低 AI 负担**，与第 5 节成本设计联动：越用越准 → 越用越省。
- **隐私**：个人词表不跨租户共享；行业词表贡献需显式开关、脱敏、可撤回（合规条款**需核实**）。
- 设置页提供「我的说法本」：可查看、编辑、删除每一条，销户时一并导出/删除（见 7.4）。

## 4. 口音与识别问题的产品侧对策

### 4.1 问题清单与对策表

| 问题 | 例子 | 产品侧对策 |
|---|---|---|
| **方言 / 口音** | 「啥」「咋」「恁」「冇」「整」「搞」「拿」「搁」「拉来了」 | ① ASR 选型需支持中文方言/口音（**需核实供应商能力**）；② **不纠正用户口音**，靠「结构化回显 + 用户改」兜底；③ 提供「我的常用说法」设置；④ 句式库按口语构造，不用书面语 |
| **数字与金额读法** | 两/俩/仨/幺/拐/勾；「块/毛/分」；「三十五」「三五」「一百二」「两块五」「一千二」 | 建**归一规则表**；「幺=1 / 拐=7 / 勾=9」等是否纳入**需核实**；不确定时**回显计算式**让用户验算；高不确定走澄清追问 |
| **商品别名与简称** | 「快乐水=可乐」「娃哈=娃哈哈」「AD 钙」「大绿棒子」 | **个人别名本 + 常用商品本**；多候选出点选卡片；选择即回流 |
| **同音词** | 帐/账、进/近、售/收、箱/香、件/见、付/负、退/推 | 结合意图与槽位类型消解；**回显只用业务词**，不展示同音错字 |
| **嘈杂环境** | 档口、菜市场、冷柜压缩机、叫卖声 | VAD + 端点检测；提供**「按住说」与「点一下说」两种模式**；引导说短句；低置信主动澄清；允许**改用手点 + 数字键盘**完成（不识字/重口音也能用） |
| **半句 / 吞字 / 重复** | 「那个……可乐……两箱」「两箱、两箱」 | 端点前留 300ms 防吞字；重复片段去重；槽位不全只追问缺的那一个 |
| **ASR 置信度低** | 识别文本明显不通 | 分级策略，见 4.2 |

### 4.2 置信度分级与澄清式追问话术（阈值均为建议值，需按实际 ASR 校准）

| 置信度 | 系统动作 | 追问话术模板 |
|---|---|---|
| 高 `≥0.85` | 直接出确认卡片 | — |
| 中 `0.6~0.85` | 出卡片 + **高亮不确定槽位** + 单轮追问 | 「你是说 **2 箱**可乐，还是 **2 瓶**可乐？」 |
| 低 `<0.6` | **不出写操作卡片**，只追问 / 提示重说 | 「没太听清，是想**进货**还是**卖货**？可以说'进了两箱可乐'这样」 |
| 无意图 / 纯闲聊 | 不调 AI、不写库 | 「我没听出要记的账～试试：'卖了三瓶可乐'」+ 给 3 个示例按钮 |

**澄清原则**

1. 一次只问 **1 个**问题，问**最关键**的那个槽位（通常是数量或方向）。
2. 给 **2~3 个可点选项**，照顾不爱说话 / 嘈杂 / 口音重的人。
3. **绝不自作主张填业务关键值**（数量、方向、金额、对象）。
4. 单会话最多 **2 轮**澄清，超过转「手动补录 / 数字键盘」（防无限追问烧钱，见 5.2）。

**追问话术模板库（示例，方言友好、短句）**

- 缺数量：「进了**可乐**，几箱啊？」
- 缺方向：「是**退给供货商**，还是**客户退回来**？」
- 单位不明：「一箱是几瓶？说一次我就记住了」
- 金额不明：「是**一件三十五**，还是**一共三十五**？」
- 时间不明：「是**昨天 11 月 14 号**那单吗？」
- 多商品同名：「你说的是**大瓶可乐**还是**小瓶可乐**？」
- 低置信：「刚没听清，再说一遍，或者点一下改」
- 指代不明：「'再来两箱'是接着**上一单**的吗？」

### 4.3 自定义别名本 / 常用商品本 / 教系统说话

| 能力 | 说明 |
|---|---|
| **别名本** | 商品 ↔ 多个说法；支持语音加（`product.alias.add`：「可乐也叫快乐水」）与**电脑版微信管理页 / 说法训练页（大屏）批量维护**；**命中优先于 AI** |
| **常用商品本** | 按录入频次自动置顶 **Top 20**（建议值，假设）；确认卡片商品选择默认展示常用，减少翻找 |
| **「老价」** | 解析为「该对象 + 该商品最近一次成交价」，回显显示**具体数值与来源日期**，不静默使用；无历史则澄清 |
| **教系统说法** | `sys.teach`：「以后我说'拿一条'就是卖一条烟」；设**电脑版微信管理页 / 说法训练页（大屏）**；**教学结果即时生效**并提示「已记住，下次就这么记」 |
| **待教学队列** | 澄清时用户给出的新说法（如「一箱=24 瓶」）自动进队列，**电脑版微信管理页 / 说法训练页（大屏）**确认后转为正式词表/换算 |

### 4.4 预期管理与产品话术

- **不承诺 100% 识别**：主打「**听不懂会问你，改一次就记住**」，把「纠错成本」转化为「越用越准」的心智。
- 首次引导：3 句示范（进 / 卖 / 查）+ 教「说短句」+ 明示**降级路径**（全程只用按钮 + 数字键盘也能记账）。
- 意义：让「电脑不熟练 / 重口音」人群**第一天就敢用**，而不是被识别失败劝退。

## 5. AI 成本的产品侧约束（用户明确要求「帮设计」）

### 5.1 成本从哪来（拆解）

| 成本项 | 驱动因素 | 备注 |
|---|---|---|
| ASR 转录 | 按音频时长 / 次数 | 长录音、环境音直接烧钱 |
| LLM 意图解析 | 按 token（system prompt + 注入上下文 + 输出 JSON） | **可优化空间最大** |
| 多轮澄清 / 二次确认 | 每轮都可能再调一次 | 必须限轮数 |
| **无效调用** | 闲聊、环境音、误触、无意图、重复录音 | **最大浪费源，且完全可以通过产品规则消掉** |
| 存储 / 带宽 / 短信 / 支付渠道费 | 低 | 见第 6 节 |

> **结论**：省钱的关键不是压供应商单价，而是 **① 减少无效调用次数 ② 减少每次调用的 token**。这恰好也是「响得快」的体验优化。

### 5.2 建议参数表（全部为建议值 / 假设，需按实际报价与压测校准）

| 参数 | 建议值 | 理由 |
|---|---|---|
| **单次录音时长上限** | **15 秒**（硬上限 20 秒） | 业务口语句式实测普遍 <10s；超长录音多半是没按停 / 环境音 / 闲聊；前端倒计时 + 到点自动收音 |
| 最短有效时长 | 0.8 秒 | 低于此判为误触，**不送 ASR** |
| VAD 静音判停 | 连续静音 **700~900ms** 自动结束 | 说完即停，不靠用户按「结束」；端点前留 **300ms** 防吞字 |
| 误触防护 | 「按住说」或「点一下 + 明显开始/结束音」；锁屏/后台不启动；间隔 <1.5s 的重复短音去重 | 档口手机在兜里最容易误触 |
| 单会话最大澄清轮数 | **2 轮** | 超过转手动补录，避免无限追问 |
| 连续录单态空闲超时 | 60 秒 | 同 3.6 |
| **Prompt 精简** | system prompt 固定；只注入「本商户常用商品 Top20 + 个人词表 + 最近 3 条上下文」 | **不注入全量商品档案**；输出强制紧凑 JSON，不输出解释文字 |
| 输出约束 | 强制 `{"intent","slots","source","confidence","clarify"}` 紧凑 JSON | 减少输出 token，便于解析与归因 |
| 缓存 / 去重 | 相同音频或相同文本 **60 秒内重复 → 复用上次解析结果** | 防重复误触重复计费 |
| 静态意图 | `sys.help` / `sys.example` / 澄清话术模板 | **不调 LLM**，直接返回本地内容 |
| 规则层命中率目标 | **≥ 40~50%**（假设，需压测） | 常规单走模板，是最大省钱点 |

### 5.3 非命令过滤器（省钱第一道闸 · 分层漏斗）

```
录音
 ① 端侧：时长(0.8~15s) / VAD / 能量 / 误触去重        → 0 成本过滤
 ② 端侧+服务端规则：纯静音、纯噪音、无有效汉字、
    明显闲聊关键词（「你好」「吃了没」「今天天气」）  → 不调 AI
 ③ 规则 / 模板层：正则 + 个人词表 + 高频句式模板
    （「进了 N 箱 X」「卖了 N 个 X」）                 → 直接结构化，不调 LLM ★最大省钱点
 ④ 意图白名单外 / 无意图：不落库、不写操作，
    最多给一次友好提示 + 示例按钮                     → 不调 LLM
 ⑤ 重复误触去重                                       → 不调 LLM
 ⑥ 仅当「规则未命中」或「槽位冲突需语义消解」        → 才调用 LLM
```

- ② 的**闲聊/环境音**是用户原话「排除非命令，然后再给 AI 解析」的直接落地。
- ③ 的**模板命中也照样出确认卡片**：省钱不省确认。
- 明确产品原则：**让 AI 只干 AI 该干的活**（歧义消解、多商品拆分、模糊指代），标准句式交给规则。

### 5.4 规则 / 模板命中优先，不调 AI

| 项 | 设计 |
|---|---|
| 模板库结构 | `句式模板 → intent + 槽位抽取器 + 缺省填充规则` |
| 模板来源 | 2.4 句式库 + 个人词表 + **用户改过的说法自动进候选模板** |
| 自动扩充 | `sys.teach` 与 3.9 纠正回流 → 高频说法升级为模板 → 命中率随时间上升 |
| 命中后 | 直接生成结构化结果 → 出确认卡片（**不调 LLM**） |
| 升级条件 | 模板未命中 / 置信度低 / 命中冲突清单（2.6）→ 才升级 LLM |
| 与成本联动 | 模板命中率每提升 10 个百分点，语音变动成本近似线性下降（见 6.4） |

### 5.5 免费额度与按次计费设计

| 项 | 设计 |
|---|---|
| **计量单位定义** | 「**1 次有效语音记账**」= 一条**成功生成确认卡片**的录音 |
| **失败/无意图不扣次** | 闲聊、环境音、误触、解析失败、用户取消 —— **一律不扣次** |
| 建议口径 | 按「**进入解析（规则层或 LLM）的录音次数**」计，但**未产生卡片的为 0 次**（兼顾成本归集与用户信任） |
| **免费额度（建议值，假设，需核实成本后校准）** | **每 30 天 100~200 次**有效语音解析（与 §6.2 的 30 天权益周期对齐）+ 基础进销存功能**永久免费**；新用户首月额外 **+100 次**试用 |
| 透明可见 | 设置页常驻「本月已用 X 次 / 免费 Y 次」；每次落账后轻提示剩余 |
| 额度为什么是这个量级 | 每 30 天 100~200 次 ≈ 每天 3~6 单，足够小微商家**形成习惯**，又不至于亏穿（见 6.4） |
| 超额后 | **不硬性断服**（档口被卡住是最差体验），走 5.6 梯度降级 |

> **计数口径（v1.1 补充）**：**用量统计按自然月归集、权益按 30 天滚动窗口计数**，前台需明确展示两种口径；实现细节需核实。

### 5.6 超出后降级策略（梯度，不「一刀切停」）

| 档位 | 触发 | 行为 |
|---|---|---|
| 额度内 | < 100% | 全功能：规则层 + LLM + 澄清 + 二次确认 |
| 达 80% | 温和提示 | 提示余额 + 推荐买**30 天权益 / 加油包**，不打断录入 |
| **超额未付费** | ≥ 100% | **仍可用「规则/模板 + 数字键盘手动补录」记核心单**（进/销/退/盘/查/收）；LLM 语义消解、一句话多商品、多轮、报表语音暂锁；**历史数据可查可导出不锁** |
| **购买权益后** | 权益生效 | 恢复全量 + 更高额度 |
| 极端异常用量 | 触发风控 | 临时限流，**绝不删数据** |

> **原则**：不拿用户数据当人质。降级是「削 AI 能力」，不是「停用账本」。
>
> **购买入口（v1.1 新增）**：购买入口在**小程序内（含电脑版微信大屏页）**，走小程序虚拟支付「30 天权益 / 语音加油包」道具直购；**不得引导到公众号 / H5 / 网站 / 客服等外部付款**（平台规则，见 6.7 与 `docs/00-决策速览.md` §5）。

### 5.7 防刷与滥用

| 措施 | 建议参数（假设，需核实） |
|---|---|
| 每商户调用上限 | 30 次/分钟、1000 次/天 |
| 同音频去重 | 60 秒窗口内相同输入复用结果，不重复计费 |
| 无意图处理 | 不扣次；连续 N 次（建议 5 次）无意图后短暂冷却并引导示例 |
| 租户隔离配额 | 单租户超额不影响其他租户，防止单户拖垮整体成本 |
| 异常告警 | 后台用量突增告警（技术实现，产品侧给规则） |
| 新账号防薅 | 设备 + 手机号维度限制试用额度（合规**需核实**） |
| 计费幂等 | 同一录音多次重试只计一次 |

### 5.8 把「省钱」做成产品卖点的可行性

| 判断 | 说明 |
|---|---|
| **可行，且是差异化** | 同类轻量进销存工具多按「席位 / 月」卖（**需核实**）；我们按「用多少、算多少」+「不听废话不花钱」，与「轻量、懒人」心智一致 |
| 三条可传播话术 | ① **「废话不收钱」**（无意图不扣次）② **「模板能听懂的，不叫 AI」**（规则层优先）③ **「失败不扣次，改一次记一辈子」**（词表回流） |
| 前台可视化（P2） | 本月「帮你省了 N 次 AI 调用」轻提示，把省钱变成「越用越聪明/越省」的游戏化正反馈 |
| 风险与边界 | 不能让「省钱」显得「功能被阉割」——话术落在**「聪明」**而非「便宜」；对外只讲**计费口径**（失败不扣次、模板优先），**不讲单价与成本**；降级策略（5.6）必须兜住体验 |

### 6.3 计费方式：**一次性购买 30 天权益 + 加油包**，不纯按次、不自动续费

| 理由 | 说明 |
|---|---|
| **平台规则不允许 MVP 自动续费** | 小程序「会员订阅」（连续扣费）准入门槛为首次发布 ≥90 天、近 30 天日均 DAU ≥1 万等（**需核实**），MVP 达不到；官方客服明确「一次性购买会员」直接接虚拟支付即可 → 改为一次性道具直购 |
| 纯按次会**抑制核心行为** | 「想到就说」是产品心智；每说一句都在算钱 → 用户不敢开口，等于自废武功 |
| 一次性买 30 天给**预算确定性** | 小微商家最怕不可控账单；一次付款、30 天额度一眼到底，且**不会静默自动扣费** |
| 额度用来**覆盖变动成本 + 防滥用** | 不是主要收费手段，是成本护栏（见 5.7） |
| 超额**降级不断服** | 保住体验，也保住数据信任（5.6）；加油包即对应「超额后补额度」 |
| **到期提醒靠自有推送** | 到期不自动扣费，靠小程序自有推送 / 订阅消息提醒复购（订阅消息能力**需核实**），且**不得引导外部付款** |
| **留存模型改写** | 由「**续费率**」改为「**复购率 / 到期回购率**」（见 6.6）；自动续费不可用的前提下，留存假设比原订阅模型更保守 |

### 6.4 定价区间与毛利逻辑（**渠道抽成计入成本**）

| 项 | 说明 |
|---|---|
| 定价下限 | 由**语音变动成本 + 渠道抽成**决定：30 天权益售价必须覆盖 `有效次数 × 单次解析成本` 与 `售价 × 渠道抽成率` |
| 定价上限 | 由「同类轻量进销存工具的心理价位」决定（**需核实**）；本产品锚在「一杯奶茶 ~ 一顿饭」带 |
| 毛利公式 | `单商户 30 天毛利 = 权益售价 × (1 − 渠道抽成率) − 有效语音次数 × 单次解析成本 − 分摊固定成本` |
| 原「毛利率 ~70%」 | **未计渠道抽成的旧假设，需下调重算**（见 6.6）；不得再作为基线 |

**敏感性示例（全部为假设参数，仅用于说明逻辑，非预测）**

```
沿用 v1.0 基础假设：30 天权益售价 ¥15（原 v1.0 基础版 ¥15 口径）；
     每 30 天有效语音 400 次；其中 50% 走规则层（近零 LLM 成本）、50% 走 LLM；
     单次 LLM 综合成本 ¥0.02、单次 ASR ¥0.004（均需核实）；
     渠道抽成按混合 ≈ 5.4%（iOS 占比 40% 假设：1%×60% + 12%×40%）。
解析变动成本 ≈ 400 × 50% × (0.02 + 0.004) ≈ ¥4.8（+ 规则层近 0）≈ ¥5 / 30 天。

① 不计抽成（旧假设）：¥15 − ¥5 = ¥10 贡献毛利（约 67% 口径）
② 计入抽成（v1.1）：¥15 × (1 − 5.4%) − ¥5 ≈ ¥14.19 − ¥5 = ¥9.19 贡献毛利
   → 渠道抽成吃掉约 ¥0.81 / 30 天（≈ 售价的 5.4%），贡献毛利率由约 67% 降至约 61%。
若规则层命中率从 50% 降到 30%：
     解析成本 ≈ 400 × 70% × 0.024 ≈ ¥6.7（+40%）
     ② 口径毛利 ≈ ¥14.19 − ¥6.7 ≈ ¥7.49 → 需提价 / 压 prompt / 提升模板命中率。
若 iOS 用户占比上升（终端结构变化），抽成率随之上升 → 毛利进一步下降。
```

> **结论**：免费额度（100~200 次 / 每 30 天）与 30 天权益售价必须由「**规则层命中率**」与「**渠道抽成率 × 终端结构**」两个杠杆共同反推校准；**企业 / 个体户主体费率、Windows 端费率口径均待核实，不得写成事实**；所有数字为产品侧假设，需按供应商报价与压测校准。

## 7. 多租户（产品视角）

### 7.1 结论：**要做，但做「轻量多租户」**

| 判断 | 理由 |
|---|---|
| **从第一天按「租户隔离」设计数据模型** | 后期改造数据归属的成本极高；账目类产品一旦串数据就是信任崩塌 |
| **但 MVP 只暴露「单商户」体验** | 用户问的是「是不是要做多租户」，不是「第一版就要连锁集团」；界面不暴露复杂度 |
| 真实高频需求 | 一个老板开 2 家店、夫妻二人各用各手机、给店员开个只能录单的号 |
| 信任底线 | 「我的账别人看不到」是小微商家买单的前提 |
| **明确不做** | 平台级多组织集团、复杂审批矩阵、跨法人结算、多级成本中心 —— 这些是重 ERP 的多租户 |

> 一句话：**数据模型多租户，产品体验单商户，连锁能力按套餐逐步放开。**

### 7.2 模型：租户 → 门店 → 员工 → 角色

```
Tenant（租户：一个老板 / 一个经营主体 = 一个账本，计费与数据归属最小单位）
  └─ Store（门店 1~N；库存/单据/盘点默认按门店隔离；「主仓/当前门店」是缺省值来源）
       └─ Member（员工；一个自然人可属于同租户多个门店；手机号/微信登录）
            └─ Role（角色，决定可见与可改范围）
```

**角色定义**

| 角色 | 权限 |
|---|---|
| 老板 | 全部 + 设置 / 用量 / 套餐 / **导出 / 销户 / 权限变更（电脑版微信管理页专属）** |
| 店长 | 本店全部业务 + 报表；**不含**权限变更、销户、全量导出 |
| 店员 | 仅录入 / 查询；**不能改价、不能看利润、不能看客户电话、不能导出** |
| 只读（P2） | 兼职会计看报表，不可写 |

**数据归属表**

| 数据类型 | 归属层级 | 跨店可见性 | 谁能改 |
|---|---|---|---|
| 商品档案 | **租户级共享** | 全店可见 | 老板 / 店长 |
| 个人别名本 / 常用商品本 | **员工级**（可提升到租户级共享） | 默认个人 | 本人 / 老板 |
| 库存 / 单据 / 盘点 / 损耗 | **门店级** | 老板可跨店汇总 | 本店有权限者 |
| 客户 / 供应商 | **租户级** | 全店可见；欠款按租户汇总、可按门店分摊 | 老板 / 店长 |
| 应收应付 / 收付 | 门店级发生、租户级汇总 | 老板可跨店 | 有权限者 |
| 报表 | 默认按门店 | 老板可跨店汇总 | 只读 |
| 语音录音原文 | 租户级、加密、限期留存（见 7.5） | 仅授权者 | 系统 |

### 7.3 单商户 vs 连锁 / 多门店边界

| 能力 | 单商户（免费 / 基础 / 专业） | 多门店（门店版，P1 起） |
|---|---|---|
| 门店数 | 1（主仓） | 2~10（P2 更多） |
| 员工数 | 1~2 | 按套餐席位 |
| 角色 | 简化（老板 / 店员） | 完整（老板 / 店长 / 店员 / 只读） |
| 跨店查询 / 汇总报表 | 无 | 有 |
| 调拨 | 不做 | P2，且调拨属 R2 需确认 |
| 库存/单据隔离 | 单店，无需隔离 | **严格按门店隔离** |
| 计费 | 按租户 | 按租户 + 门店数阶梯 |
| **升级路径** | — | **一键升级为多门店**：现有数据挂到「总店」，**不迁移、不丢数据、不改历史单号** |

### 7.4 数据导出与销户

| 项 | 设计 |
|---|---|
| 导出 | 老板随时可导出**全量**（商品 / 单据 / 库存 / 往来账 / 个人词表），格式 Excel / CSV；**导出属 R3，禁止语音直接执行**，**电脑版微信管理页二次确认**；**导出文件经微信转发（文件传输助手 / 保存到微信 / 微信内预览分享，API 可用性需核实），不做网页下载**；导出**绝不含其他租户数据** |
| 销户 | 老板在**电脑版微信管理页**申请 → 二次确认 → **冷静期 7 天**（建议值，需核实合规）→ 彻底删除（含录音原文、个人词表、备份）→ 出具**删除回执** |
| 冷静期内 | 可随时撤销销户；账号只读冻结，不产生新费用 |
| 产品卖点 | 「**账是你的，随时能全带走**」——对抗小微商家「被平台绑住」的顾虑 |

### 7.5 隐私与账目敏感性

| 原则 | 落地 |
|---|---|
| 账目 = 商业机密 | **不跨租户共享**；不做平台级账目数据 pooling 训练，除非用户显式开启且脱敏 |
| 语音录音原文 | 建议「解析成功后仅保留**结构化结果 + 原文文本**，音频默认 **7~30 天后删除**」（参数**需核实合规要求**）；设置页明示留存策略 |
| 个人词表 / 别名本 | 属**用户资产**；销户一并删除或一并导出 |
| 权限最小化 | 店员看不到利润、客户电话、欠款全貌 |
| 合规入口 | 预留「授权 / 撤回授权 / 查看与删除我的数据」入口；具体条款 **需核实**（涉及手机号、语音、经营数据） |
| 可写进产品的明示承诺 | 「**不卖数据、不拿你的账训练给别人、不投广告**」 |

### 8.2 MVP 边界（第一版到底做什么 / 不做什么）

**做**

> 一个商户、一个主仓、1~2 个人，用小程序**语音说一句话**记「进 / 销 / 退 / 盘 / 查 / 收」，看一眼确认卡片、按一下大按钮落账；记错了 10 分钟内能撤；**电脑版微信大屏页能看账、改档、导出（导出文件经微信转发，不做网页下载）**。

- 8 个业务域 + 系统辅助；17~20 个 P0 intent（见 8.1）
- 确认环节完整（回显 / 大按钮 / 二次确认 / 超时 / 编辑 / 撤销反做 / 回流）
- 成本护栏完整（过滤器 / 模板优先 / 免费额度 / 降级 / 防刷）
- 基础口音兜底（归一表 / 别名本 / 澄清话术 / 手动补录降级路径）
- 单商户体验 + 多租户数据模型
- 免费版 + 30 天权益定价骨架（计费口径可见）

**不做**

- 多门店 UI / 调价 / 利润报表 / 复杂权限 / 批次保质期 / 打印 / 开放 API / **电脑版微信端语音（P2，麦克风可用性需核实）** / 扫码 / 一句话多写命令 / 大额收付 / 行业词表
- **独立网页版 / PC Web / H5（含 Vite+React 工程）**
- **账号密码登录**（仅微信身份；手机号 + 验证码兜底可 P1）
- **自动续费订阅**（MVP 准入门槛不达标，准入门槛需核实）、**外部付款引导**（公众号 / H5 / 网站 / 客服）
- MVP 依 P12 **可不放付费入口先免费内测**，但不得引导外部付款

### 8.3 成功指标（目标值均为**假设 / 待校准**）

| 指标 | 定义 | 目标值 | 为什么 |
|---|---|---|---|
| **语音一次成功率** | Top1 意图正确 + 关键槽位全对、无需修改即确认 | 成熟用户 ≥ **85%**，新用户 ≥ **70%** | 核心体验指标 |
| **确认率** | 生成的卡片中被确认落账的比例 | ≥ **90%** | 低 = 解析或回显没讲清 |
| **「改一下」率** | 确认前发生编辑的比例 | ≤ **15%**，且逐周下降 | 衡量词表回流是否有效 |
| **单条命令成本** | 综合 ASR + LLM 的有效解析成本 | ≤ **¥0.02**（**需核实报价**） | 直接决定毛利 |
| **规则层命中率** | 未调 LLM 即完成结构化的比例 | ≥ **45%**（假设，需压测） | 最大省钱杠杆 |
| **无意图过滤率** | 非命令录音在进 LLM 前被拦下 | ≥ **90%** | 成本护栏有效性 |
| **平均录入耗时** | 从开口到落账 | ≤ **8 秒**（对比手工打字快 3 倍以上） | 「快捷」是否成立 |
| **撤销率** | 落账后被撤的比例 | ≤ **3%** | 高 = 影响预览没讲清后果 |
| 低置信追问后成功率 | 澄清后最终确认的比例 | ≥ **80%** | 衡量追问话术 |
| **首次购买转化率**（原「免费 → 付费转化」） | 免费用户首次购买 30 天权益 / 加油包的比例 | **8~12%**（**假设，需核实**） | 同 6.6；自动续费不可用，首次购买是唯一转化入口 |
| **权益到期复购率** | 30 天权益 / 每 30 天到期后主动回购（含加油包）的比例 | **50~70%**（**假设，需核实**） | 替代原「续费率」；留存模型从续费率改为复购率（见 6.3 / 6.6） |
| 次日 / 7 日留存 | — | 逐版本观察 | 「越用越顺」的代理指标 |

8. **收款走小程序虚拟支付（`wx.requestVirtualPayment`）道具直购**（「30 天权益」/「语音加油包」），**发货只以「发货推送」为准**且**发货回调锁定云开发云函数消息推送，不自建 `notify_url` 域名；云托管消息推送不作为虚拟支付发货路径**（接 `xpay_goods_deliver_notify` 等事件；前端 `success` 不作依据，`query_order` 查单兜底 + 幂等），发货 = 给该 `tenant_id` 的 `usage_quota` 加额度 / 延长权益有效期；**取消自动续费订阅**，留存模型按复购率。
9. **不做独立网页版 / PC Web / H5（含 Vite+React 工程）、不做账号密码登录、不做自动续费订阅、不引导外部付款**；电脑端 = 电脑版微信里的同一小程序（同一 AppID、`resizable` 大屏适配），导出经微信转发不做网页下载；**小程序备案 T01 并行启动**。
